# Plan: Pinecone Free Tier + Local Chatbot SPA

## Context

**Current state**: ~50K chunks with 1024-dim BGE-large-en-v1.5 embeddings in local ChromaDB (~3.8 GB) + BM25 pickle index. Chatbot uses Anthropic SDK with tool use over local search.

**Goal**: Host the vector index on Pinecone's free tier (serverless) and build a local single-page application chatbot that queries it.

## Pinecone Free Tier Constraints

| Constraint | Limit | Our Usage | Fits? |
|---|---|---|---|
| Storage | 2 GB | ~50K vectors * 1024 dims * 4B = ~200 MB vectors + ~160 MB text metadata = ~400 MB | Yes |
| Indexes | 5 | 1 | Yes |
| Namespaces | 100 per index | 1 (or per-product if desired) | Yes |
| Read units | 1M/month | ~33K queries/month at 30 RU each | Yes |
| Write units | 2M/month | 50K upserts at initial load, occasional re-index | Yes |
| Region | AWS us-east-1 only | Fine | Yes |
| Inactivity | Paused after 3 weeks | Need keepalive or accept cold start | Manageable |
| Metadata | 40 KB per vector | ~4 KB per vector (url + title + text) | Yes |
| Hybrid search | Sparse+dense with dotproduct metric | Replaces local BM25 + RRF | Yes |

**Key insight**: Pinecone serverless supports native sparse-dense hybrid search, which replaces our entire BM25 + Reciprocal Rank Fusion pipeline with a single API call.

## Phase 1: Pinecone Backend Adapter (Est: 3-4h)

**Why**: Decouple the search layer from ChromaDB so the same search pipeline works with either backend.

### 1.1 Create `cyberark_rag/pinecone_backend.py`

New module that implements the same search interface as ChromaDB but backed by Pinecone.

```python

        """Query Pinecone with optional hybrid sparse-dense search."""
        ...

    def hybrid_search(self, query: str, top_k: int,
                      filter_product: str | None = None,
                      alpha: float = 0.7) -> list[dict]:
        """
        Full hybrid search in a single Pinecone call.
        alpha=1.0 is pure dense, alpha=0.0 is pure sparse.
        Default 0.7 matches our current vector_weight.
        """
        ...
```

- Uses `pinecone[grpc]` client for lower latency
- Sparse vectors generated by `pinecone-sparse-english-v0` model (free tier: 5M tokens/month) OR local BM25-style sparse encoding
- Dense vectors from existing BGE-large-en-v1.5 (generated locally, same as now)
- Metadata stored per vector: `url`, `title`, `product_category`, `chunk_index`, `content_type`, `original_text` (truncated to 2000 chars to stay safe on storage)

### 1.3 Modify `search.py` to support both backends

Add a factory pattern:
```python
def create_searcher(backend: str = None) -> DocumentSearcher:
    backend = backend or Settings.SEARCH_BACKEND
    if backend == "pinecone":
        return PineconeSearcher(...)
    return DocumentSearcher(...)  # existing ChromaDB path
```

The `PineconeSearcher` implements the same `search()` interface but delegates hybrid search to Pinecone's native sparse-dense support instead of local BM25 + RRF.

### 1.4 Create `scripts/upload_to_pinecone.py`

CLI tool to push the existing local index to Pinecone:
1. Read all chunks from ChromaDB (or from scraped_docs + re-chunk)
2. Generate dense embeddings (BGE-large, same as current)
3. Generate sparse vectors (using Pinecone's built-in sparse encoder OR local TF-IDF)
4. Batch upsert to Pinecone in chunks of 100
5. Report progress and final stats

```bash
$ python scripts/upload_to_pinecone.py

Creating index 'cyberark-docs' (1024 dims, dotproduct)...
Processing 50,234 chunks...
  Batch 1/503: 100 vectors upserted
  ...
  Batch 503/503: 34 vectors upserted
Done. 50,234 vectors in index. Storage: ~380 MB / 2,000 MB free tier.
```

## Phase 2: Chatbot SPA Backend (Est: 3-4h)

**Why**: The existing `chatbot_cli.py` is terminal-only. A FastAPI backend enables both the browser SPA and potential future mobile/desktop clients.

### 2.1 Create `cyberark_rag/api.py`

```

GET  /api/products      -- List products
GET  /api/stats         -- Index stats
GET  /api/health        -- Health check + Pinecone connectivity
GET  /                  -- Serve SPA (index.html)
```

**Chat endpoint** (SSE streaming):
```python
@app.post("/api/chat")
async def chat(request: ChatRequest) -> StreamingResponse:
    """
    Stream chat responses using Server-Sent Events.
    Reuses CyberArkChatbot from chatbot.py for tool use loop.
    """
    async def event_stream():
        async for event in chatbot.chat_stream(request.message, request.history):
            if event.type == "text":
                yield f"data: {json.dumps({'type': 'text', 'content': event.text})}\n\n"
            elif event.type == "tool_use":
                yield f"data: {json.dumps({'type': 'tool', 'name': event.name})}\n\n"
            elif event.type == "tool_result":
                yield f"data: {json.dumps({'type': 'tool_result', 'name': event.name, 'summary': event.summary})}\n\n"
        yield f"data: {json.dumps({'type': 'done'})}\n\n"

    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

**Request/Response models** (Pydantic):
```python
class ChatMessage(BaseModel):
    role: Literal["user", "assistant"]
    content: str

class ChatRequest(BaseModel):
    message: str
    history: list[ChatMessage] = []
    model: str = Settings.CHATBOT_MODEL

class SearchRequest(BaseModel):
    query: str
    top_k: int = Field(default=5, ge=1, le=20)
    product_filter: str | None = None
    use_hybrid: bool = True
```

## Phase 3: SPA Frontend (Est: 4-6h)

**Why**: Browser-based chat UI is more accessible than a terminal REPL and supports rich formatting (markdown, syntax highlighting, clickable links).

### 3.1 Technology choice

**Vanilla JS + Web Components** (no build step, no node_modules):
- Single `spa/` directory with `index.html`, `app.js`, `styles.css`
- Zero build tooling -- just static files served by FastAPI
- Uses native `EventSource` API for SSE streaming
- Markdown rendering via `marked.js` (CDN)
- Syntax highlighting via `highlight.js` (CDN)
- Total bundle: <50 KB (excluding CDN libs)

Rationale: This is a developer tool, not a consumer product. No React/Vue/Svelte overhead for what is fundamentally a chat input + message list + search panel.

### 3.4 Features

- **Conversation history**: Maintained in browser memory, sent with each request

- **Direct search mode**: Toggle to search panel for raw search results without LLM

- **Dark/light mode**: Follows system preference, toggle available
- **Keyboard shortcuts**: Enter to send, Shift+Enter for newline, Ctrl+K to clear

## Storage Budget (Pinecone Free Tier)

| Component | Size Estimate |
|---|---|
| Dense vectors: 50K * 1024 dims * 4 bytes | ~200 MB |
| Sparse vectors: 50K * ~100 nonzero dims avg * 8 bytes | ~40 MB |
| Metadata: 50K * ~4 KB avg (url + title + text + fields) | ~200 MB |
| Index overhead | ~60 MB |
| **Total** | **~500 MB / 2,000 MB** |

Comfortable margin. Could support up to ~200K chunks before hitting limits.

## Monthly Usage Budget (Pinecone Free Tier)

| Operation | Units | Estimate |
|---|---|---|
| Queries (hybrid, 1024-dim, top-10) | ~30 RU each | ~33K queries/month |
| Casual usage (10 queries/day) | 300/month * 30 RU | 9,000 RU / 1M |
| Heavy usage (100 queries/day) | 3,000/month * 30 RU | 90,000 RU / 1M |
| Re-index (50K upserts) | 50K WU | 50K / 2M |

Well within limits for a personal/team tool.

## Risk Mitigation

| Risk | Mitigation |
|---|---|
| Pinecone free tier removed | ChromaDB remains as fallback (backend toggle) |
| Index paused (3-week inactivity) | Weekly keepalive cron job |
| Latency (us-east-1 from other regions) | ~100-200ms per query, acceptable for chat UX |
| Anthropic API costs | Use claude-haiku-4-5 for cost-sensitive deployments |
| Sparse encoder token limit (5M/month) | Generate sparse vectors locally with TF-IDF fallback |
